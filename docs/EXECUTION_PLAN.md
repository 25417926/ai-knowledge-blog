## 3. 本轮：引用锚点修复（2026-10-16）

**症状。** `citations` 表 274 条引用里 260 条 `chunk_id` 为 NULL。界面上不报错——
历史回放的出处卡片静默消失，只有查库才看得见。

**根因。** `import_vault` 每导入一次就把该 post 的 chunks 全删重插（`init_db.py:296`），
`chunks.id` 是自增主键，旧 id 全部消失，外键 `ON DELETE SET NULL` 顺手把回链擦成 NULL。
**只要再跑一次 `init_db` 引用就断一次**——这不是一次性故障，是每次导入都复现的设计缺陷。

**处置。** 锚点换成稳定业务键，不再依赖派生数据的自增主键：

| | 旧 | 新 |
|---|---|---|
| 锚 | `chunk_id`（自增，重导即失效） | `post_slug` + `heading_path` + `quote` |
| 稳定性 | 每次导入必断 | slug 由 `import_vault` upsert，永不漂移 |
| 可读性 | 引用不自包含，必须 join 到 chunks | 自包含：哪篇、哪节、原话是什么 |

引用自此即使文章被改写、切分块被重建、文章被删，仍能完整显示出处。

**迁移。** 见 `server/app/database.py` 的 `_migrate_citations_anchor()`，旧行按两种办法回捞：
chunk 尚存活的直接取 slug/heading；其余用 `quote` 前缀在现有 `chunks.body` 里比对
（`quote` 落库时就是 `body.strip()[:400]`，是精确逆运算，不是模糊匹配）。
回捞不到的保留原样（`post_slug` 为空，前端不渲染），**不删数据**。

实测结果（2026-10-16）：

| | 条数 |
|---|---|
| 迁移前有锚的引用 | 14 / 274 |
| 迁移后带出处的引用 | **239 / 274**（14 条原本存活 + 225 条捞回） |
| 未能回捞 | 35（集中在被重新抓取过的收藏稿——那部分原文本身已替换，捞不回是应该的） |

**验收**：连跑两次 `init_db`（chunks 全量重建，id 从 3072 漂到 3333），
引用条数稳定在 274 / 239 不变——修复前同样操作会把它们全部清成 NULL。
`GET /api/ask`（历史回放）68 轮问答共 239 个出处卡片恢复渲染；
`POST /api/ask` 与 `/api/ask/stream` 的新引用均正确落 `post_slug + heading_path`。

**刻意没做。** 不改 `import_vault` 的「删除重建」策略——chunks 是检索用的派生数据，
重建本身没有错，错的是把它易变的主键当锚。

## 4. 本轮：友链改后台维护（2026-10-16）

**为什么改。** 友链原先是 `src/lib/friends.ts` 里的编译期常量——加一个人要改代码、重新构建。
它本来就是会变的数据，不该住在源码里。

**改法。** 入库 + 后台 CRUD，复用文章那套后台外壳：

| 层 | 落点 |
|---|---|
| 表 | `friends`（name / href / description / tags / created_at / updated_at） |
| 公开读 | `GET /api/friends`；前台 `/friends` 改 `force-dynamic` 动态取数 |
| 后台写 | `GET/POST /api/admin/friends`、`PUT/DELETE /api/admin/friends/{id}`，界面 `/admin/friends` |
| 种子 | `content/friends.json`，**只在 `friends` 表为空时灌** |

**两个刻意的选择。**

1. **只写库，不写文件。** 文章必须写回 md（否则下次 `init_db` 把后台改动反向覆盖），
   而友链不进 RAG、不进图谱、没有对应文件，自然没有那条坑。
   种子的「表空才灌」是配套保险：后台删掉的条目不会被下一次 `init_db` 复活。
2. **`href` 只放行 `http(s)://`。** 它最终渲染成 `<a href>`，放行 `javascript:` 等于开一个注入口子。
   重复链接返回 409，不为此加数据库唯一约束。

**验收**：连跑两次 `init_db`，第二次友链新增 0 条（种子不复活）；
`POST` / `PUT` / `DELETE /api/admin/friends` 全程可用，`/friends` 与后台列表同步刷新；
生产构建通过，`/admin/friends` 静态预渲染、`/friends` 转为动态。

## 5. 本轮：收藏摘抄改笔记体例 + callout 渲染（2026-10-16）

**为什么改。** 收藏稿原先套的是「是什么 / 核心观点 / 对我的启发」三段式——那是报告体，
与手写笔记的骨架（`>` 导语 → `## 一、` 分节 → `- **关键词**：说明` → 收尾 callout）不是一路，
混在同一个 vault 里一眼能看出哪篇是机器写的。

**处置。**

| 层 | 落点 |
|---|---|
| 摘抄体例 | `scripts/clip.py`：`SUMMARY_PROMPT` 重写为笔记体；`one_liner()` 改为「只认首行 `>` 当导语，否则退回标题」；笔记正文去掉 `## 三段式总结` 外壳 |
| callout 渲染 | `src/lib/markdown.ts` 新增 `remarkCallout`：mdast 阶段把 `> [!type] 标题` 换成 `div.callout.callout-<type>` + `.callout-title`；**颜色与图标全走 CSS 变量**，19 个类型，不引图标库 |
| 样式 | `src/app/globals.css`：`.callout-*` 的 `--callout-rgb` / `--callout-glyph`，标题色 `color-mix(类型色 62%, 正文色)`——浅色不发飘、深色不刺眼 |
| 问答口径 | `agent_chat.py` 两处 system prompt：出自收藏的片段以「原文存档」为准 |

**验收**：离线 11/11（把 `markdown.ts` 单文件编成 CJS 直调 `renderMarkdown`，覆盖无标题 / 行内加粗
标题 / 未知类型 / 嵌套 / 列表内 / 折叠标记，以及「普通引用块不受影响」）；浏览器 15/15（真实页面
无 `[!tip]` 残留，19 个类型的图标与底色都在，双主题按亮度验可读性）。两篇收藏已用真实 LLM 重跑。

**踩到的两个坑**（都不报错，只出错）：① callout 正则结尾**不能写 `$`**——mdast 里软换行是 text 节点
value 里实打实的 `\n`，`(.*)$` 整体匹配失败且静默；② **先清理段落、再判断是否删段落**，顺序写反会
因为 `length === 0` 成立而顺手删掉下一个子节点，正文整段被吞。

## 7. 本轮：落地导览（2026-10-17）

**问题。** 首页原本只有「最新文章轮播 + 说说照片 + 状态卡」：能看出「有什么新东西」，
看不出「这里在讲什么、我该从哪读」——「AI 快速定位访客想了解什么」的反面一直空着。

**做法。** 两块，都不新增检索能力：

| 位置 | 改动 |
|---|---|
| `src/components/TopicGuide.tsx`（新） | 首页「主题导览」区块：左边是把《知识地图总览》提上来的 START HERE 主入口卡，右边按分类各一张主题卡，卡里直接铺该主题的文章标题（最多 4 条 + 「还有 N 篇」），底部「进入主题 →」跳归档 |
| `src/app/page.tsx` | 接上 `listCategories()`（此前已导出但零调用），在轮播与状态卡之间插入导览区 |
| `src/components/TimelineControls.tsx` | 新增主题筛选条，与标签条并列；两条都补了小标（「主题」/「标签」） |
| `src/app/timeline/page.tsx` | 把分类传进筛选区；`?category=` 生效时页头说明当前主题并给回首页导览的出口 |
| `src/lib/categoryLabel.ts`（新） | 分类显示名：`clippings` → 「收藏摘抄」。**只影响显示**，URL 与库里的值一律不动 |

三个判断：

1. **「知识地图」这一类要挑出来单独做主入口。** 它是索引本身，不是一个内容主题；
   混在网格里就变成「一篇讲目录的文章」，跟旁边那张 Java 卡不是一个层级。
2. **主题卡里直接铺文章标题**，不只给一个「3 篇」的数字——这样首页到任一篇笔记是**一步**，
   而不是「首页 → 归档 → 文章」两步。验收条款就是照这个写的。
3. **英文分类名只在界面上换中文**，URL 保持原值：`?category=clippings` 依然有效，
   库里与接口里也全是原值，只多了一层显示映射。

**验收**：`next build` 通过（18 条路由全产出）；浏览器 28/28 —— 导览区块与 TOPIC GUIDE 小标在、
主入口卡指向 `/posts/知识地图总览`、主题卡 4 张且 `clippings` 显示为「收藏摘抄」、
点主题卡里的标题一步落到文章页且标题一致、点索引卡一步进索引页、

## 8. 本轮：关系网召回（2026-10-17）

**问题。** 文章之间唯一的边是显式 `[[双链]]`。链接密集的文章下方有「出链 / 反向链接」两块，
但**孤立文章那两块全是空的**——读者顺着读不下去，助手能用的证据也只有关键词检索那一档。

**做法。** 在 `links` 之外算出隐式边，落到文章页新增的「相关文章」区块。三档证据：

| 证据 | 权重 | 为什么算 |
|---|---|---|
| 共同标签 | 3.0 / 个 | 作者自己贴的，最经得起解释 |
| 同被一轮问答引用 | 2.0 / 次（摊薄） | 助手回答过一次就说明这两篇被同时用上了，等于现成的共现证据 |
| 内容重合 | ×20 | 标题 + 摘要 + 切分块的 IDF 加权余弦；没有标签、没有共引时唯一的线索 |
| 同分类 | 0.5 | 弱信号，给同类目但没标签的文章留一条路 |

四个判断：

1. **刻意排除已有显式双链的文章**（两个方向都算）。出链/反链另有面板，「相关文章」补的是那两块
   空着的时候；重复列一遍只会让人以为推荐重复了。P1 原话「跟这篇有关**但没互相链接**的文章」正是此意。
2. **内容重合不在原计划里，是实测加上去的。** 只用「共同标签 + 共同被引用」跑：两篇孤立文章里
   《周刊》能召回 6 篇，而《4. More Control Flow Tools》（英文 Python 文档，只有 `收藏` 一个标签、
   从没被问答引用过）**只有 1 篇**——验收要求 2~3 篇，过不了。没有这一档，孤立文章就是功能的盲区。
3. **共引按「该轮被引篇数 - 1」摊薄。** 一轮引 2 篇是强证据；答泛问时一轮引 3 篇（当前库仅 1 例），
   那 3 篇两两之间都要打折，否则一次概览回答就能把它们连成团。`co_citations` 仍记轮次数
   （界面上写「同被 N 轮问答引用」），只有排序用摊薄后的权重。
4. **内容重合算「凑数」档**：仅在看得清理由的不足 3 条时补进来，且永远排在证据之后。
   《4. More Control Flow Tools》因此拿到 3 篇（1 篇真证据 + 2 篇内容相近），而不是把 6 个位置填满噪声。

**分词抽成了公共模块。** `services/keyword.py` 收 `PARTICLES` / `STOPWORDS` / `tokenize` 与
`idf_table` / `overlap`，`agent_chat.retrieve` 改为 import 它——分词是「同一个词在两处必须切得一样」
的东西，留两份实现必然漂移（问答里命中、相关推荐里不命中，不报错只是变差）。
**打分公式没有合并**：检索是「查询 vs 切分块」（标题 3.0 / 小节 1.6 / 正文 1.0 加权），
相关推荐是「文档 vs 文档」（对称），问的不是同一件事。

**补了什么。** `server/tests/` 5 个文件 / **127 条**，1.9 秒跑完，**不连库、不发网络请求、不需要 Key**：

配套：`server/pytest.ini`（`pythonpath = .`，从 `server/` 跑 `python -m pytest`）、
`server/requirements-dev.txt`（只多一个 pytest，运行依赖不动）。

**用例分两类，这是刻意的。** 一类是契约（标题权重高于正文、未入库的词不得分、幂等、边界闭区间）；
另一类是**现状锁定**（characterisation）——照搬旧实现留下的口径，改了就该红，逼人先看一眼再动：

- `_score_chunk` 的 idf 里「文档总数」用的是 `len(tokens)`，不是切分块总数。所以查询里塞进没命中的词，
  命中词的 idf 反而变大（`log(1+4/1) > log(1+1/1)`），部分抵消分母 `sqrt(len)` 的稀释。

这两条都已写进 docstring：P2 若改成真实块总数，命中分会整体下移，**`RAG_MIN_SCORE` 必须一起重标**。

**变异检查：证明测试真的会红。** 只跑绿不算数，故意改坏三处再跑——

| 改坏 | 结果 |
|---|---|
| `_score_chunk` 标题权重 3.0 → 2.0 | 红（`test_title_beats_heading_beats_body` 等） |
| `tokenize` 去掉虚词过滤 | 红（`test_particles_cut_the_run`） |
| `split_chunks` 去掉围栏保护 | 红（`test_fenced_code_keeps_hash_lines_in_body`） |

**写测试时撞出来的三个真问题。**

1. **切块 bug（已修）。** 围栏代码块里的 `# 安装依赖` 被当成一级标题：代码块被劈成两半、
   注释行从正文里消失（检索也就搜不到那一行），`heading_path` 变成 `Strategy:  Create a new collection`
   这种注释行。现库实测有 **4 个块围栏不配对**，全在那篇 Python 文档的收藏稿里。
   修法是给 `split_chunks` 加围栏状态机（```` ``` ```` / `~~~` 进出，围栏内不认标题）。

2. **`overlap`「完全重合 = 1.0」只在 idf 齐平时成立。** 分子是 idf 之和、分母是两个平方和开方之积，

   给相关文章调阈值时别拿 1.0 当基准。

## 10. 本轮：向量混合检索（2026-10-17）

**目标**：关键词保精度、向量保召回。**结论：管线建好后一度默认关闭，当天下午拿到本机
`qwen3-embedding:4b` 后已启用**（见 §10.5）。中间的关键转折不是「接了个模型」，
而是发现真实 embedding 的余弦**各向异性极强**——不减均值就完全没法用。

### 10.1 做了什么

| 层 | 内容 |
|---|---|
| 向量服务 | 新 `server/app/services/embedding.py`：provider = `none`（默认）/`hash`（本地字面近邻）/`openai`（任何 OpenAI 兼容 `/embeddings`） |
| 存储 | 向量存 `chunks.embedding` BLOB，**应用层算余弦**，不引向量库。每个 BLOB 自带 10 字节信封：magic(3) + provider(1) + 维度(2) + **模型指纹(4)** |
| 检索 | `retrieve()` 命中分 = 关键词分 + `4.0 × max(0, cos − 0.25)`（**这是首次建成时的标定，
接入真模型后已改成 `10.0 × max(0, cos − 0.15)`，且 cos 先减语料均值，见 §10.4**）；`score` 仍是排序分，另返回 `kw_score` / `vec_score` 便于排查 |
| 运维 | 新 `scripts/embed_chunks.py`（幂等补向量、`--rebuild`、`--stats`）+ `init_db --embed` |
| 评估 | 新 `scripts/eval_retrieval.py`：16 条固定查询，并排输出关键词 / 混合的位次、hit@4、MRR |
| 测试 | `tests/test_embedding.py` 40 条（信封、余弦、融合、`/embeddings` 响应处理） |

**信封为什么要存模型指纹**：两个不同模型可能同为 1024 维，光看维度会把它们当成同一个
空间，余弦照算不误、结果全错、还不报错。指纹把「换模型」也变成硬约束——对不上就当没有
向量（宁可少召回一次，也别静默算错）。

**融合公式为什么这么配**：`cos = 0.5` 恰好加满 `RAG_MIN_SCORE = 1.0`，低于地板一分不加。
于是**老路径的分数逐位不变**，那套照着「真实提问 1.5~3.8 / 闲话 0.57」标定的阈值一个字没动，
`best_score()` 的闸门、Mock 分支、工具调用全都不用改。

### 10.2 实测：为什么默认关闭

**① 本机没有语义向量可用。** DeepSeek 的 `/embeddings` 三个候选模型名全 404；
本机 Ollama 有 `qwen3:4b` / `gemma3:4b`，但都是对话模型，且拉取新模型要联网（当时超时）。

**② 内置 hash 方案没有区分度。** 它用 `keyword.tokenize` 的特征做带符号哈希，本质是
「没有 IDF、没有长度归一的字面重合」。实测 8 条查询里，正确文章的位次：

| 查询 | 正确块位次 | 该篇最高 cos |
|---|---|---|
| 池子满了之后新来的活儿交给谁 | 55 | 0.048 |
| 一条请求从进门到落地都经过哪些环节 | 87 | −0.025 |
| 两段文字像不像用什么量 | 21 | 0.071 |
| JUC 线程池核心参数（原词） | 1 | 0.659 |

原词能到 0.66，改写只剩 0.05 量级——和无关文本分不开。而且一篇英文 Python 文档经常
在中文提问里排第一（哈希撞桶）。**当默认就是拿噪声冒充召回**，所以 `none` 是默认值，
`hash` 只作「管路能不能跑通」的自检（`--provider hash`）。

**③ 顺带量出的真问题：关键词通道没有块长度归一。** 长文（《周刊》）靠字面面积大通吃，
这是那 5 条改写查询漏掉的直接原因。加上块长度归一后：

| 指标 | 现状 | 加长度归一 |
|---|---|---|
| hit@4（同口径探针） | 10/16 | **11/16** |
| MRR | 0.501 | **0.624** |
| 门槛 1.0 下过闸 / 闲话误放 | 10/16 · 0/13 | 需降到 0.5：10/16 · **1/13** |

排序变好、闸门变差。闸门决定「答不答」，只凭一半证据不能动——**本轮不改打分公式**，
把它连同 tf、idf 的偏差记入 §12 技术债 8，等有语义向量一起重标。

### 10.3 只有动手才知道的两件事

1. **LLM 路径会自己改写查询**。评估里「池子满了之后新来的活儿交给谁」在检索层是 0 命中，
   但同一句话走 `/api/ask` 能返回 4 条正确引用——因为模型把问题改写成「线程池 拒绝策略」
   再调 `search_posts`。所以检索层的缺口在配了模型的路径上被掩盖了，暴露得最彻底的是
   Mock 模式。这也意味着：向量档真正该服务的是「没有模型帮忙改写」的场景。
2. **不用 Milvus**（用户问过）：它只是存/查向量的容器，不产生语义能力；126 个块在应用层
   全量算余弦 <1ms；标准部署要 Docker + etcd + MinIO，与「零外部服务依赖」冲突。
   `milvus-lite` 是唯一不碰 Docker 的路子，但仍要 embedding 供应商，且 Python 3.13 轮子
   不保证有。真到数据过万、配了语义模型那天，换后端只动 `embedding.py` 一个模块。

### 10.4 启用：qwen3-embedding:4b 与「先减均值再算余弦」

2026-10-17 下午用户在本机 Ollama 拉好 `qwen3-embedding:4b`（2560 维，Q4_K_M），
`/v1/embeddings` 通、返回已归一，126 个块补向量 **10.7 秒**，查询热态 **0.18~0.65 秒**。

**直接套原公式会得到「假效果」。** 三组数据：

| 现象 | 数字 |
|---|---|
| 任意两段不相关的中文余弦 | 中位 **0.899**（45 对里最低 0.806） |
| 正确答案 vs 无关答案 | 0.936 / 0.925，**中间没有缝** |
| 闲话提问（8 条）的最高块 | 0.86~0.905，**每条都指向同一篇《周刊》** |

原因有两个：① **各向异性**——所有向量带一个巨大的公共分量，余弦全挤在 0.85 以上；
② **枢纽点**——那篇周刊内容最杂，任何提问都离它不远。此时 `VEC_FLOOR=0.25` 会让
**每个块**白拿 +2.6 分：「今天中午吃什么好」原本 0 结果，接上向量后跑到 2.496
（闸门 1.0），助手会拿一篇技术周刊回答午饭问题。

**修法：检索前先把查询与文档一起减去全站语料均值，再算余弦**（`embedding.centroid` /
`center`，均值按「块数 + 最大 id + 向量总字节」缓存，语料一变自动重算）。同一个模型：

| 空间 | 闲话最高分区间 | 向量单路 hit@4 | 向量单路 MRR |
|---|---|---|---|
| 原始余弦 | 0.860~0.905 | 12/16 | 0.658 |
| **减均值后** | **0.102~0.149** | **15/16** | **0.942** |

阈值随之重标：`VEC_FLOOR = 0.15`（正好卡在闲话最高分之上）、`VEC_WEIGHT = 10.0`
（用 16 真 + 8 闲话的网格扫出来，`floor×weight` 25 组里唯一同时满足「hit@4 15/16、
MRR 0.906、闲话 0/8 放行」的区间）。合成结果：

| 指标 | 纯关键词 | 关键词 + 向量 |
|---|---|---|
| hit@4 | 11/16 | **15/16** |
| MRR | 0.536 | **0.906** |
| 原词 / 改写 | 6/6 · 5/10 | 6/6 · **9/10** |
| 闲话提问被放行 | 0/8 | **0/8** |

**顺手修掉一个更隐蔽的坑**：`import_vault` 对每篇笔记都 `delete + insert` 全部 chunk，
原先后台**保存一篇文章就会清空全站向量**，而且不报错——只是召回悄悄变差。两处补上：
① `import_vault` 在删块前按「标题路径 + 正文」把旧向量存下来，内容没改的块原样继承
（实测全量重导后 126 个向量一个不少）；② 新增 `services/embedding_job.py`，
后台保存与收藏管道在导入后自动补未覆盖的块（best-effort，失败只记日志，不影响保存）。
CLI `embed_chunks` 也改成调用同一份 `plan()` / `fill()`，三个入口不再各写一套。

**剩下那 1 条未中**（"公司内部资料怎么让模型用上"）在向量单路里排第 17。走 `/api/ask`
却答得对——模型自己把查询改写成了「RAG 检索增强生成」，§10.3 第 1 条说的掩盖效应依旧存在。

**三个设计决定**：

1. **路径放在 `/api/admin/*`**，不是计划原来写的 `POST /api/clippings`。写入口要过
   `require_admin`，而前端后台一律走同源 `/api/admin/*` 才能带上 SameSite 的 cookie；
   公开的 `routes/clippings.py` 只留 `GET /clippings/pdf` 这只读出口。
2. **一次只跑一条**：进程内 `asyncio.Lock`，第二条直接 409。两条并发会同时写 vault、
   同时 `import_vault`，笔记文件名还可能撞在一起。
3. **删除必须连 Post 一起删**：`import_vault` 只 upsert 从不删，只删 clippings 行会留下
   「搜得到却打不开」的文章。按 `source_path` 反算 slug，连 chunks/links/post_tags 一起清。

**怎么做的**

- 流程整体从 `scripts/clip.py` 搬到 `services/clipping.py`，CLI 只剩参数解析与打印。
  CLI 与网页各写一套必然漂移——这套东西有摘抄体例、PDF 版式、索引补 chunk 三个容易走样的地方。
- 库函数不读 stdin：粘贴内容从参数进来（`article_from_paste(title, pasted)`），标题留空才取第一行。
  Web 侧才能把表单文本直接传下来，并保留「第一行当标题」的老习惯。
- **同步活全部 `asyncio.to_thread`**：httpx 抓取与 reportlab 造 PDF 都是阻塞调用，跑在事件循环里
  会把整个后端卡住十几秒（后台同时还有别的请求在跑）。
- **抓不到正文返 422 而不是 500**：消息里直接写「把全文粘贴到正文里再试」，页面收到 422 就展开粘贴区。
  这是这条管道唯一的降级口子，也是公众号反爬的日常。

**顺手修的真 bug**：摘抄是长输出任务（8000 字输入 + 结构化输出），沿用闲聊那档
`LLM_TIMEOUT=20s` 会卡在边界上——实测两次里失败一次，而且失败只是静默降级成「总结失败」。
`chat_completion` 加了 `timeout` 参数，摘抄单独给 90s，实测 14s 完成且稳定。

1. `/api/posts/{slug}` 对缺失文章返回 **200 + `null`**（前端据此 `notFound()`），不是 HTTP 404。

## 15. 本轮：访客意图聚合（2026-10-20）

对齐三条诉求里的「定位访客意图」。日志本来就全（`agent_turns` 87 次提问 / `citations` 293 条），
缺的只是**把日志读成结论**的那一层。所以这一轮没有新表、没有新写入路径，只有一条只读接口加一页视图。

### 15.1 做了什么

| 层 | 位置 | 说明 |
|---|---|---|
| 聚合（纯函数） | `server/app/services/insights.py` | 归一化 / 意图分流 / 聚类 / 汇总，输入是提问列表，输出是四组排好序的视图 |
| 取数 | `GET /api/admin/insights?days=0`（`routes/admin.py`） | `user` 轮与紧随其后的 `assistant` 轮配对，引用算在**回答**那一轮上 |
| 视图 | `/admin/insights`（`src/app/admin/insights/page.tsx`） | 四个数字 + 意图分布 + 高频问题 + 内容缺口 + 被问到的文章 |
| 闭环入口 | 缺口行上的「为它写一篇」 | 跳 `/admin/posts/new?title=<访客原话>`，编辑器按 `?title=` 预填标题（正文留空） |

### 15.2 三个判据（比代码更值得记）

1. **零引用 ≠ 内容缺口。** 寒暄（"你好"、"谢谢"）本来就不该有引用，混进缺口列表会把整页冲成废话。
   所以缺口只收信息类意图；寒暄单独归 `chitchat`，仍计入总数（不粉饰引用率）。
2. **高频问题先聚类再计数。** 按原字符串分组会把"向量怎么接"与"怎么接向量"拆成两条各 1 次，
   看起来像"什么都只问一次"。聚类闸门是**双条件**：词集 Jaccard ≥ 0.5 **且** 意图相同——
   只看相似度会把"怎么做 X"和"为什么 X"并成一条，而它们是两个不同的缺口。
3. **同一篇被一次问答引 3 段 ≠ 三个访客在找它。** 文章排行按「被几次问答引用」排，段数只作副标。

### 15.3 实测（全部历史，83 次提问 / 1 个博客会话）

- 引用率 **87%**（72/83），零引用 11 条，平均响应 3.9s、每次回答平均 3.1 段引用。
- 意图分布：怎么做 30（97% 有引用）/ 是什么 24（75%）/ 其他 24（92%）/ 原理解释 4（75%）/ 寒暄 1。
- 高频问题第一名「线程池的核心参数怎么设」**23 次**（验收脚本反复问同一句），第二名"这篇文章讲了什么" 7 次。
- 内容缺口 7 条，最扎眼的是「海之霸秘方是什么」4 次（站内确实没有这篇）、"这篇讲了什么" 2 次。
  点「为它写一篇」→ 编辑器标题已预填访客原话，实测一致。

### 15.4 两个坑

1. **`ASSISTANT_SLUG` 是 `assistant`，库里 agent 的 slug 是 `librarian`。**
   直接 `select(Agent).where(slug == ASSISTANT_SLUG)` 查不到 → 接口返回全零骨架，页面像"没有数据"，
   不报错。必须走 `agent_chat._resolve_agent()`（它按 `meta.blogAssistant` 挑）。
2. **同一个 agent 名下混着非博客入口的会话**（历史遗留 `librarian:town`），
   把它们算进来会让缺口里冒出「我叫阿国」这类不该被回答的句子。
   现在只统计 `<slug>:<SESSION_KEY>` 那个会话；**一条都对不上时退回全部**——
   宁可数据略脏，也不要因为 key 改名而悄悄变空白页。

### 15.5 验收

- 单测：`server/tests/test_insights.py` **38 条**（全库 279 条，2.5s 全绿）。守的是判据，不是 SQL。
- 接口：`days=0` → 83 次；`days=1` → 2 次（今天那两句），窗口过滤生效。
- 浏览器：桌面 1440 / 移动 390 / 浅色主题各一遍，四个数字对得上、7 条缺口都在、
  点「为它写一篇」标题预填一致、无横向溢出、0 控制台错误。
- 未做：意图分类仍是关键词规则（"今天晚饭吃什么" 落进 `other` → 会进缺口），
  要更准需接模型，另开一档再谈。

## 16. 本轮：出处从「检索流水账」改成「引用清单」（2026-10-20）

现象是真的：某一轮回答正文只标了 `[1][5]`，下方「出处」却列出 **7 段 / 4 篇**——
五分之四的内容这次答话根本没用到。读者看到的不是依据，是检索日志。

### 16.1 判断：不是「段落 vs 整篇」的二选一

这两者不是同一层的东西：段落**属于**文章。所以分两级，而不是二选一：

- **卡片 = 一篇文章**（点开才看段落）——这就是"弹整篇"那一层；
- **展开 = 这篇被引的那几段**（小节名 + 原文摘录 3 行 + 「读整篇 ↗」）——这就是"弹段落"那一层。

真正该砍的不是段落，而是**没被引用的段落**。

### 16.2 四条规则

1. **只列正文标出来的 `[n]`。** 没标的一律收进折叠行「另有 N 篇 M 段检索命中（本答未引用）」，
   默认收起。检索命中不作废、照旧落库（`citations` 是「查过什么」的证据，访客意图页还要用它）。
2. **同篇多段合并成一张卡。** 标题行是《文章》`› 小节`（单段）或《文章》`› N 段`（多段）。
3. **正文 `[n]` 变成可点标号**，点了就地展开对应卡片并滚到可见。用原生 `<details>` 做状态，
   不去 React 里再搬一份「哪张卡展开着」——这类同步最容易写漏。
4. **兜底不藏出处。** 正文一个标号都没有时（Mock 路径、或模型忘了标），退回「全部展示」。
   宁可多列，也不能因为模型漏标就让读者以为没有依据。

### 16.3 顺手修的两处

- `StepTrail` 折叠行那句「引用 N 篇」传的是 `sources.length`，也就是**段数**；现在传去重后的篇数。
- 历史回放 `read_log` 只回 `slug/heading`，不回 `quote` → 刷新前后两套观感。现在补上，
  实时（done 事件）与回放同一组字段。
- 单段卡的展开区不再重复小节名（标题行已经写了）。

### 16.4 实测

| 场景 | 改前 | 改后 |
|---|---|---|
| turn 204（JVM 内存模型） | 7 张卡 | **1 张卡**（同篇 2 段） |
| 实问「余弦相似度为什么常归一化」 | 4 张卡 | **1 张卡**（同篇 2 段） |

单测 279 全绿（后端仅多回一个字段）；桌面 1440 / 移动 390 / 浅色主题三遍：
点标号展开的正是那一段、无横向溢出、0 控制台错误。

### 16.5 再收一步：未引用的命中挪进思考链

第一版把「另有 N 篇 M 段」放在出处下方，仍然是一条占位的横线。既然它讲的是「这次查了什么」，
就该跟检索步骤待在一起——于是挪进思考链展开区，摘要行只留一个数字：

```
▾ 检索 1 次 · 引用 1 篇 · 另命中 1 篇
   1  检索"余弦相似度 归一化"              命中 4 条 · 4256ms
   另命中 1 篇 2 段，本答未引用
     向量检索与余弦相似度 › 2 段 ▾
```

这样默认态下，出处区永远只有「撑起这句话的那几篇」。旧数据 / Mock 路径没有 `tool_trace`
（思考链整块不渲染），未引用的命中仍退回出处下方的折叠行，不能让它们凭空消失。

验收：桌面 1440 / 移动 390 / 浅色三遍，默认态出处分别 2 张 + 1 张卡（两条历史回答）、
展开思考链出现「另命中 1 篇 2 段」、点标号展开的正是那一段、无横向溢出、0 控制台错误。

## 17. 本轮：三条冒烟 e2e + 检索档位（2026-10-20）

P5-3 与 P5-5 一起做，因为它们是同一类问题：**「坏了也没人知道」**。
前者是页面整体崩掉时没人自动发现，后者是检索悄悄降级、界面毫无变化。

### 17.1 e2e：只补三条，但每条都能真红

`e2e/smoke.mjs`，`npm run e2e`，三条：

| 断言 | 凭什么算过 |
|---|---|
| 首页三区块 + 数据通路 | `section[aria-label=…]` 三个都在（博主资料 / 最新文章 / 主题导览）；**再加一条**：最新文章区里至少一个 `/posts/` 链接——区块在但数据断了照样渲染空壳 |
| 软 404 | 状态码**必须 404**（500 说明渲染时抛错）；且出现「这条街没有这栋楼」 |
| 后台闸门 | 访问 `/admin/posts` 后 URL 变成 `/admin/login`，`h1` 是「后台登录」，且侧栏项「访客意图」不出现 |

四条纪律：

1. **不碰 LLM。** 一次问答要等本机模型十几秒，塞进冒烟之后没人愿意跑。
2. **先探活再启动浏览器。** 前端或后端没起时，报「不可达 + 先起服务」，而不是一个 20 秒超时堆栈。
3. **`playwright-core` 不写死路径。** 依次试 `PLAYWRIGHT_CORE` → 项目 `node_modules` →
   `NODE_PATH` → 托管工作区；仓库里不出现用户名。
4. **控制台零错误要精确豁免。** 软 404 那条必然会报一条「status of 404」，
   但**不能**写成「含 404 就忽略」——那会连首页 chunk 拉不到一起吞掉。
   现在是按**文档 URL** 豁免：只有那一次 `page.goto` 的目标地址能免。

**红绿都验过**：
- 绿：`4/4 通过`（3 区块 · 5 个文章链接 · h1「赛博小镇 · 一座会说话的知识小镇」）。
- 红：把断言里的 `主题导览` 改成 `主题导览ZZZ` 后，该条失败、**其余两条继续跑**、
  汇总 `3/4`、退出码 1——证明断言真的在探测，而不是恒真。
- 预检：`E2E_BASE` 指向空端口时直接给「前端不可达 + 先起服务」，退出码 1。

### 17.2 检索档位：先纠正一个错误前提

P5-5 原本写「`embedding.ready()` 为假时自动退回关键词」。**实测不是这样**：
`ready()` 只检查 `base_url` 与模型名在不在，Ollama 停掉后它**仍然返回 True**，
失败发生在每次 `embed_query` 内部（`EmbeddingError` → 返回 None → 静默退回关键词）。
所以「加个 ready 判断」解决不了任何问题，必须**真探一次**。

| 层 | 做法 |
|---|---|
| 探测 | `embedding.probe()` 打一次 `/models`，`is_success` 才算通；异常一律 false，探测自己不许抛（它挂在 `/api/health` 上） |
| 缓存 | 30 秒。health 会被面板反复拉，没必要每次都打 Ollama；30 秒的滞后对排查够用 |
| 分档 | `mode`：`hybrid` / `keyword`；`reason`：`''` / `off`（没配）/ `hash`（只是字面哈希）/ `unreachable`（配了连不上）。**「没配」与「连不上」必须分开**——`reachable` 对前者是 `null` 而不是 `false`，否则界面把「本来就没开」一直画成故障 |
| 界面 | 面板输入框下方一行 10.5px：绿点「语义检索 · qwen3-embedding:4b」/ 琥珀点「仅关键词检索 · 语义模型连不上」；细节进 `title` |

**`ready()` 的语义刻意没动**（`test_ready_stays_true_when_unreachable` 钉住）：
它被检索路径与补向量任务当开关用，改成探活会让「配了就跑」的逻辑全部走形。

**顺手修掉一个真坑：系统代理。** 这台机器上 `HTTP_PROXY` 是设着的、`NO_PROXY` 为空，
httpx 默认会把 `127.0.0.1:11434` 也交给代理 → 代理返回 **502**。
表现是：配置全对、模型也在跑，却每次都退回关键词，日志里只有一行 warning。
现在本地地址（`127.0.0.1` / `localhost` / `::1` / `0.0.0.0`）走 `trust_env=False`，
远程 embedding 服务仍走代理。**探测与检索共用同一个客户端**，否则会出现
「探测说通、检索还是降级」这种自相矛盾。

### 17.3 验收

- 单测：`289 passed / 3.44s`（新增 10 条：状态分档 7 + 客户端代理 3）。
- 档位**正反都验**：
  - Ollama 停着 → `/api/health` 报 `reachable:false, mode:keyword, reason:unreachable`，
    面板显示「仅关键词检索 · 语义模型连不上」，琥珀点。
  - 起 `ollama serve` → 同一接口变成 `reachable:true, mode:hybrid`，面板显示
    「语义检索 · qwen3-embedding:4b」，绿点。**能翻转才算数**。
- 三视图：桌面 1440 / 移动 390 / 浅色主题，`overflow=0`、控制台 0 错误。
- e2e：`npm run e2e` → 4/4。

### 17.4 剩余

§14.2 只剩 **P5-6 编辑器预览**（正文仍是纯 textarea）。另有一处与本轮无关的旧问题：
`BlogAssistant` 里 `articleSlug` 的正则仍是 `^/blog/(.+)$`，而文章路由早已是 `/posts/[slug]`，
所以「只搜本文」实际上永远不会自动打开——要修得连提示文案一起改，单独一轮处理。

## 18. 本轮：把 Ollama 从默认配置里摘掉（2026-10-20）

**动因是运维成本，不是效果不好。** 语义召回确实把 hit@4 从 11/16 拉到 15/16、MRR 0.536 → 0.906，
但代价是「装完博客还得再装一个 4B 模型 + 养一个常驻服务」，加上系统代理把
`127.0.0.1:11434` 叼走（§17.2）那类问题，出问题的表现是**静默降级**。
博客这个体量不值得为召回多背一层运维面。

**做法：只摘依赖，不删能力。** 代码、阈值、BLOB 向量、评估脚本全部保留。

| 处 | 改成 |
|---|---|
| `server/.env` | `EMBEDDING_PROVIDER=none`，其余四行删掉 |
| `.env.example`（根） | 原来只有三项且缺 `PROVIDER` —— 照那个模板填**根本不会生效**（默认 none）。补齐五项并注明必须一起给 |
| `server/.env.example` | 主推改远程 API 示例；Ollama 降为「历史备注」，附上当初的收益数字与摘掉原因 |
| 面板档位行 | `reason === 'off'` 时**整行不渲染**。默认档是正常状态，挂黄灯等于让每个装完就跑的人来问一次「我配错了吗」 |

## 19. 本轮：两处既有问题（2026-10-20）

§18 收尾时留下两条，都属「不崩、但会让人对系统失去信任」的那类。

### 19.1 低分引用不再挂出来

**现象**：问「今天天气怎么样」，正文写「没有找到相关内容」，下面却整整齐齐列着 4 篇出处
（score 0.777 / 0.388 / 0.388 / 0.388）。读者的结论只能是出处是装饰品。

**根因**：`box.citations` 收的是**检索到的全部条目**——模型调几次工具就攒几条；
`RAG_MIN_SCORE` 只在两处用来决定「要不要提醒模型诚实收尾 / 要不要烧 LLM」，
**从未用于过滤回传的引用列表**。

**修法**：抽出 `citations_within_gate()`（`agent_chat.py`，紧挨 `VEC_FLOOR` 定义），
两条路径共用——LLM 的 `_run_tool_agent` 返回前、Mock 的 `talk` 预检索后。
判据与闸门同源，全项目只判一次，前端不抄阈值。

**刻意整组丢，不逐条过滤。** 引用序号是 `register` 时按追加顺序发的，正文里的 `[n]`
按它对；中间抽掉一条会让后面的标号整体错位，读者点开的是另一段原文。
代价是「一条强命中 + 几条同篇低分」时低分的也会留着——那几条至少在同一篇相关文章里，
比标号错位轻得多。

Mock 路径**排除 `article_overview` 分支**：它是按文章取段落，分数本来就不由查询决定，
套闸门会把「这篇文章讲了什么」变成「没找到」。

### 19.2 「只搜本文」的开关从来没出现过

**现象**：文章页助手面板上那两个按钮（「只搜当前这篇」「这篇文章讲了什么？」）从不渲染。

**根因**：`BlogAssistant` 里 `articleSlug` 用 `/^\/blog\/(.+)$/` 从 `pathname` 取 slug，
而文章路由早就是 `/posts/[slug]`。正则永远不匹配 → `articleSlug` 恒为 `null` →
整块 UI 不渲染。**没有任何报错**，所以从路由改名那天起就坏了。

**修法**：`/^\/posts\/([^/]+)\/?$/`（slug 只有一段，`(.+)` 会把 `/posts/a/b` 也吞进来）。

**顺手把它变成第 4 条 e2e**，因为这类失效只有自动化能发现：
- 正向：文章页出现「✓ 只搜当前这篇」；
- 反向：首页**不该有**——正则若写成什么都匹配的 `/(.+)$/`，这条会红；
- slug 从首页现取，不写死（写死了会先因为「文章没了」而红，掩盖真正要盯的东西）。

顺带修了 e2e 里一个静默坑：打开助手面板靠 `window.dispatchEvent`，
**派发早于 hydration 就等于打给没人听的电话**——面板不开、也不报错、断言在 20 秒后超时。
现在 `openAssistant()` 轮询重发直到可见，失败时给一句人话。

## 21. 关系网换 three.js 画布（2026-10-20）

起因是「动画太慢」：`/graph` 上一版是**静态** SVG，220 轮力导在渲染期跑完就结束，
没有一帧动画；悬停只换 opacity。这一轮把它换成 three.js 正交相机画布，SVG 退到
「首屏 / 无 WebGL / 减弱动效」三档兜底。

### 21.1 改了什么

| 文件 | 变动 |
|---|---|
| `src/lib/graph.ts` | **新增**：把 `undirectedEdges` / `layoutGraph` / `nodeRadius` / `shortTitle` / `neighboursOf` 抽出来。两层必须逐像素重合，布局只能有一份 |
| `src/components/LinkGraphGL.tsx` | **新增**：three.js 画布 + 一层 DOM 标签（真实 `<a>`，可聚焦）、悬停/拖拽、主题跟随、入场动画 |
| `src/components/LinkGraph.tsx` | 改成两层外壳：SSR 画 SVG，探测到 WebGL2 后动态挂画布并交叉淡入；`data-graph-node` 只在当下起作用的那一层 |
| `package.json` | 新增 `three@0.170` + `@types/three`（分包 490KB，只在 `/graph` 加载） |

动画本身是四件事，都不贵：入场 420ms、按 18ms 错峰；静止时每个点按自己的相位
做 ±1.5 单位的呼吸；悬停用逐帧插值放大到 1.32 并淡出无关节点；拖拽时节点跟手、
连线实时跟随。**没有**跑实时力导——那会让「稳定」变成需要等待的事情，而布局
本来就已经算死了。

### 21.2 踩到的坑（都能再咬一次）

1. **y 轴翻向下 → 面朝向翻转 → 全被背面剔除。** `OrthographicCamera(0, W, 0, H, …)`
   的投影矩阵行列式为负，默认 `FrontSide` 把整张图当背面扔掉。现象极具误导性：
   `renderer.info.render.calls === 45`、`getError() === 0`、控制台没有任何报错，
   但 `readPixels` 全 0、截图全空。修法是材质 `side: DoubleSide`；顺便
   `frustumCulled = false`（12 个点不值得让视锥剔除参与判断）。
2. **入场动画不能改尺寸。** 第一版让节点从 0.2 倍缩放大，而 SVG 正在同时淡出，
   两层尺寸不一致，看起来像「先缩一下再长回来」。改成从外圈 16% 处收拢 + 纯淡入。
3. **标签层不能用 `translate` 工具类。** 每帧要写 `style.transform`，和内联的
   `-translate-x-1/2` 会互相覆盖；拆成外层（跟手写 `translate3d`）+ 内层（负责居中）。
4. **canvas 不要设 `touch-action: pan-y`。** 图在容器里横滚，写死 pan-y 会把
   移动端的左右滑动吃掉，提示行就成了谎话。触屏只做点击，纵向滚动交回浏览器。

### 21.3 验收

## 23. 右侧目录真正跟随滚动（2026-10-20）

用户反馈「右边这个 table 往下翻的时候需要跟随下翻」。代码里一直有 `sticky top-24`，
但滚动时整块目录跟着正文一起滚出视口。

### 23.1 根因：sticky 的滑动空间是 0

`sticky` 元素的移动范围由**父元素高度减自身高度**决定，不是「有没有写 sticky」。

```
<aside class="order-first lg:order-none">        ← grid item，默认 stretch，高度 = 整行（≈8644px）
  <nav class="hidden lg:block">                  ← block，高度只有内容（282px）★
    <div class="sticky top-24">…</div>           ← 可滑动距离 = 282 - 282 = 0
```

实测 `getComputedStyle(div).position === 'sticky'`、`top: 96px`，一切「看起来对」，
只是 `nav` 高度等于 `sticky` 高度，滚 1200px 后 `rect.top = -612`（跟着滚出去了）。
这类失效没有报错、没有视觉异常，只有滚动时能看出来。

### 23.2 修法

`nav` 加 `lg:h-full`（撑满 grid 行高 = aside 高度），配 `max-h-[calc(100vh-8rem)] overflow-y-auto
overscroll-contain`——目录本身超过一屏时在内部滚动，别把末尾条目顶出可视区。

改的是 `src/components/Toc.tsx` 一行 className，其余不动。

### 23.3 验收

- 结构探测：`agent-多智能体协作`（8 项）滚 0 / 900 / 2400 / 5662 / 8536，目录 `top` 依次
  `587 → 96 → 96 → 96 → 96`；`提示工程的结构化写法`（3 项）同样全程 96。
- 新增 e2e 第 7 条「文章页目录滚动跟随」：取 `wordCount` 最大的一篇（短文章目录本来就矮，
  失效也不明显，拿它当样本等于白测），滚到 1400 与 `docH * 0.75`，断言 `rect.top ∈ [0, 120]`。
- **验过能真红**：临时去掉 `lg:h-full` 重新构建 → `滚到 1400 时目录 top=-813`、
  `7/8 通过`、退出码 1；还原后重建 → `8/8`、退出码 0。
