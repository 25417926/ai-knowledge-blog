# 检索的收尾：为什么「没找到」下面还挂着四条出处

在博客助手里问一句「今天天气怎么样」。

正文很诚实：没有找到相关内容。但正文下面，整整齐齐列着四张出处卡片，分数是 `0.777` 和三个 `0.388`。点开其中一张，是一段讲余弦相似度的笔记——它跟天气没有任何关系。

这不是模型的问题，也不是检索「召回错了」。**这四段确实被检索到了**，它们只是不该被当成出处展示。真正出错的地方在收尾环节：从「检索到什么」到「给读者看什么」这一段路，中间少了一道闸门。

顺着这一条查下去，同一个环节上还有四个同类问题。它们的共同特征很明显：**系统在它不确定的时候，选择了沉默地做点什么，而不是干净地什么都不做。**

## 坑一：引用列表从来没被过滤过

先看数据是怎么流的。模型带着工具跑一轮，每调一次检索工具，命中就往 `box.citations` 里追加。问题在于「检索到了」和「答得出」是两件事，而这个列表只记前者：

```python
# 收尾时用的判据只有一处
if box.citations and box.best_score() < RAG_MIN_SCORE:
    ...  # 提醒模型诚实收尾：「没找到就说没找到」
```

也就是说，`RAG_MIN_SCORE`（`1.0`）只决定了两件事：要不要提醒模型别硬答、要不要真的去烧一次 LLM。**回传给前端的引用列表，从头到尾没被这个阈值碰过。** 于是正文说「没找到」，下面却挂着四条 0.388。

修法是把这个判断抽成一个函数，在两个出口前各调一次：

```python
def citations_within_gate(citations: list[dict]) -> list[dict]:
    """只有过了闸门的才配当「出处」。"""
    if not citations:
        return []
    return citations if max(c["score"] for c in citations) >= RAG_MIN_SCORE else []
```

这里有个刻意的取舍：**整组丢，不逐条过滤**。

理由是引用序号。正文里的 `[n]` 不是随便编的，它按 `register` 时的追加顺序发放：第 3 次注册的块就是 `[3]`。如果中间抽掉一条低分的，后面的标号会整体前移一位，读者点开 `[4]` 看到的是另一段原文——**为了少显示一条不相关的出处，把所有标号都弄错了**，这笔交易明显不划算。

整组丢没有这个问题：要么这一组可信（最高分过线），要么干脆不给。

> [!warning] 边界：按文章取段落的那种分支不能套闸门
> 「这篇文章讲了什么」是另一条路径——它按文章取段落，分数不由查询决定。
> 套上闸门会把「这篇文章讲了什么」变成「没找到」，所以这条路要单独排除。

## 坑二：「没标 `[n]` 就全展示」是好意办的坏事

闸门修完，闲聊干净了。但正常回答里还有一层浪费：正文只标了 `[1][5]`，卡片却列了 7 张——同一次检索里顺带命中的段落，全被摆了出来。

这一层其实是前端的一个兜底在起作用：如果正文一个标号都没有（Mock 路径、或者模型忘了标），那就把全部出处展示出来。这个兜底的动机是好的——**宁可多列，不能藏出处**，总比读者看不到来源强。

但它把「模型没标」和「模型标了、只是只标了几个」当成了同一件事：

```tsx
// 正文标了 [n] 就只认可这些：没标的多半是检索顺带命中，收进折叠行
const cited = citedNumbers(m.content);
const keep = cited.size > 0 ? cited : null;   // ← 一个标号都没有时，退回全展示
const primary = groupSources(m.sources, keep);
```

现在的分工是两级：

- **卡片 = 一篇文章**（"整篇"这一层），展开是这篇里被引的那几段（"段落"这一层）；
- 正文没标号、但确实检索到的，挪进思考链的折叠行：「另命中 3 篇 5 段，本答未引用」。

改完的效果，同一轮对话从 7 张卡变成 1 张（同篇两段）+ 一行折叠。阅读体验的差别不是「少了六张卡」，而是**「出处」这个词重新有了含义**——它现在只指撑起这句话的那几篇。

顺带修掉一个更隐蔽的 bug：思考链上那句「引用 N 篇」传的是 `sources.length`，那是**段数**不是篇数。同一篇里引了三段，会被说成引用了三篇。这种错不会让人报错，只会让人对数据的信任少一点。

## 坑三：slug 对不上，接口静默返回全零骨架

访客意图页刚上线时，打开是一片空白：提问 0 次、引用率 0%、缺口 0 条。但数据库里明明有 83 次提问、87% 的引用率。

原因是一行看起来毫无问题的查询：

```python
ASSISTANT_SLUG = "assistant"
agent = (await session.execute(select(Agent).where(Agent.slug == ASSISTANT_SLUG))).scalar_one_or_none()
```

库里那个 agent 的 slug 是 `librarian`，`assistant` 只是配置里给「博客助手」这个身份起的名字。查不到 → `agent is None` → 所有按 agent 过滤的统计全部归零。**接口 200、结构完整、字段都在，只是每一个数字都是 0。**

这类故障最贵的地方在于它长得像「没数据」。第一反应如果是「是不是还没人提问」，就会去翻日志、翻埋点、翻数据库连接，而真正该做的第一件事是**核一下 ident 对不对**。

修法不是在查询里硬编码 `librarian`——那是把同一个耦合换个地方埋。调的是已有的解析函数：

```python
async def _resolve_agent(session: AsyncSession, slug: str) -> Agent:
    if slug == "assistant":
        # 按 meta.blogAssistant 标记来找，而不是按 slug 字面量
        agent = next((a for a in candidates if "blogAssistant" in a.meta ...), None) or row
    else:
        agent = (await session.execute(select(Agent).where(Agent.slug == slug))).scalar_one_or_none()
    if agent is None:
        raise ValueError(f"找不到角色：{slug}")
    return agent
```

顺手还发现同一 agent 名下混着非博客入口的会话（小镇端自报家门那句「我叫阿国」也进了统计，成了「内容缺口」之一）。于是统计口径收紧成 `<slug>:<SESSION_KEY>`；但**一条都对不上时退回全部**——宁可数据脏一点，也不能在筛选条件变化后静默变成空白。

## 坑四：摘要空串，把关系网拖糊

「相关文章」的推荐打分里，标题和摘要是一起算的：

```python
token_set(title + summary)   # 摘要为空 → 这一半权重直接蒸发
```

摘要为空不是「少一点信息」，而是**推荐质量整体下降，且没有任何提示**。它会以「最近的相关文章怎么越来越不准」的形式，晚两周才被人注意到。

根因是保存路径上摘要可以被留空，而留空就真的写了个空串进 frontmatter。修法是在保存时兜一句：

```python
# 摘要留空不再等于「往 frontmatter 塞一个空串」：确定性抽取兜一句。
# 这里刻意不走 LLM——保存要快（模型一卡 2~10 秒），而且 Mock 摘要一旦入库
# 不会在配好 Key 之后自动更新。想让模型写，是编辑器里那个按钮的事。
summary = body.summary.strip() or summary_svc.extract_summary(title, body.content)
```

这条的取舍值得单独说：**为什么不让 LLM 直接生成摘要**。两个理由，都不是洁癖。

一是保存要快。模型一次调用 2~10 秒，保存按钮转十秒，人就会开始重复点。

二是更麻烦的那个：Mock 摘要是占位文本，一旦入库就**不会自动刷新**。等哪天配好了 Key，库里躺着的那批摘要仍然是占位符，而且没人知道哪些是占位。所以抽取（确定、毫秒级、可单测）站在保存路径上兜底，模型只在你主动点「AI 优化」时出场。

抽取本身也不是 `split('\n')[0]` 那么简单。真实语料里，第一行经常是围栏代码块、`> 来源：https://… · 收藏于 …`、一行公式、或者以冒号结尾的引导句。最后定下的判据是：**行内有中文标点，就一定是人写的句子**——比「中文占比超过多少」稳得多，因为它不依赖阈值。

## 坑五：裸 `sqlite3` 删数据，留下孤儿切分块

清理测试稿时图快，直接开了个 sqlite 连接：

```sql
DELETE FROM posts WHERE slug = 'tmp-test';
```

删完看着没问题：列表里消失了。但检索仍然能把这篇的内容捞出来——因为 `chunks` 表里那一行还在。裸连接默认 `foreign_keys=OFF`，级联删除不生效；应用里（SQLAlchemy 会话）外键是开着的，所以从 API 删就没这个坑。

修法只有两种：走 API 的 DELETE，或者手动补一句

```sql
DELETE FROM chunks WHERE post_id NOT IN (SELECT id FROM posts);
```

这条被记成规矩，不只是因为「留了脏数据」，而是因为**脏的位置很刁**：它不影响页面、不影响列表、不影响构建，只影响检索质量——而那是最难用眼睛验的地方。

## 一个还没解决的坑：讲了 11 次的东西检索不到

上面五条都修了。但还有一条，目前只是被记录了，没修。

站里那篇《混合检索：BM25 与向量的分工》，全文出现 `RRF` 十一次，整节在讲它怎么把两路结果融合。问「RRF 是怎么把两路结果融合的」，检索不到它。

原因在打分函数里：

```python
for token in tokens:
    idf = math.log(1 + len(tokens) / freq)
    if token in title:
        score += 3.0 * idf      # 标题命中
    elif token in heading:
        score += 1.6 * idf      # 小节标题命中
    elif token in body:
        score += 1.0 * idf      # 正文命中
```

两个老问题：

**没有 tf。** `RRF` 在这篇里出现十一次和出现一次，得分完全一样。
**没有长度归一。** 长文档天然能命中更多 token，分数被篇幅抬起来；短的、精确的段落反而吃亏。

两件事叠起来的后果是：一个只在**正文**里反复出现的关键词（权重 1.0），打不过一个恰好出现在别的文章**标题**里的泛词（权重 3.0）。文章块数从 126 涨到 219 之后，这个问题更明显了——分母变大，精确描述的那篇被稀释得更厉害。

这条债的修法不是调权重，而是把 `_score_chunk` 换成真正的 BM25（tf 饱和 + 文档长度归一）。之所以没顺手改，是因为它会动到全站排序——改完必须重跑一遍检索评估脚本，看 hit@4 和 MRR 是涨是跌，而不是凭一两道题的手感。**没有对照数据的调参，只是把旧偏差换成新偏差。**

## 收尾

这五个坑连起来看，讲的是同一件事：**检索系统的信用，不在它答得准的时候，而在它说不的时候。**

答得准，读者会多问几句；答不准，读者会怀疑一次。但如果「不知道」的时候下面还挂着四条无关出处，「知道」的时候也会被当成装饰品——你没法区分哪次是真的。

所以那些看起来最不像功能的地方，往往才决定这套东西能不能被信：

- 不过线的引用，整组不给；
- 没被正文引用的命中，挪进「查过什么」而不是「撑起这句话」；
- 找不到 agent，宁可抛错也不要返回全零骨架；
- 摘要留空，用确定性抽取兜住，别让静默的质量下滑积累成习惯；
- 删数据走应用层，别让孤儿块留在检索里。
