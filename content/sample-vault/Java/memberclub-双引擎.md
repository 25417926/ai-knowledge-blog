# memberclub 双引擎：扩展点与流程链

> 项目：memberclub-master（虚拟商品交易中台：办会员、卖券包）
> 核心结论一句话：**扩展点引擎 = 前台的通讯录（找对人），流程引擎 = 后厨的流水线（干对事）。**
> 深入版（源码逐行解读）见项目目录：`doc/两大引擎深入详解.md`、`doc/项目学习指南.md`

---

## 一、两个引擎的人话翻译（餐厅比喻）

一个请求进来，就像顾客点单，全过程分三步：

### 第一步：单子上自带两个标签

请求里带着：**业务线（我是谁：抖音 / 课程 / demo会员）+ 场景（我要干嘛：提单 / 取消 / 售后）**

### 第二步：前台查通讯录（扩展点引擎 ExtensionManager）

前台拿着两个标签翻通讯录，逐级降级：

1. `抖音 + 提单` 的专属负责人 → 找到就他干
2. `抖音 + 默认做法`
3. `通用 + 提单`
4. `通用 + 默认`（万金油兜底，永远有人接活）

**这就是"逐级降级"的意义：新业务线只需要登记自己与众不同的那一小块，其余自动落到默认实现。**

### 第三步：后厨流水线（流程引擎 FlowChain）

找到的厨师按固定工序干活：锁库存 → 扣配额 → 建订单 → 收款。每个工序（FlowNode）有三个约定：

- **干完了** → 打勾（success）
- **后面某步炸了** → 前面干过的工序**倒着挨个"吃后悔药"**（rollback）：建了单就删单、扣了配额就还回去。这是不依赖分布式事务框架、手搓的"部分失败也能收拾干净"方案
- **这步不用干** → 举牌"跳过"（SkipException），不算出错、不回滚（如：该商品不涉及库存）

## 二、为什么要这么设计（动机比代码重要）

不用引擎的写法 = if-else 屎山：提单方法里 `if (抖音) ... else if (课程) ...`，取消、售后方法里再各来一遍。每加一条业务线，几十个方法全要改。

用引擎之后：**新业务线 = 新开一个 plugin 包，只写"我和别人不一样"的几行**，主流程一行不动。

设计哲学：**把"不变的骨架"沉淀下来，把"会变的部分"做成可插拔的插件。**

## 三、万能三段论：注册 → 路由 → 执行

看任何框架先问三句：**谁注册？怎么找到？找到后怎么执行？**

| 例子 | ① 注册 | ② 路由 | ③ 执行 |
| :--- | :--- | :--- | :--- |
| memberclub 双引擎 | 启动时 `@ExtensionProvider` 扫进 Guava Table | `bizType+scene` 四级回退查表 | FlowChain 节点链 + 逆序补救 |
| Spring IoC 容器 | `@Component` 扫描进容器 | `getBean()` / 按类型注入 | 直接调 Bean 方法 |
| 拦截器 / Filter | 注册进拦截器链列表 | 按请求路径匹配 | `chain.doFilter` 链式传递 |
| 餐厅（生活版） | 员工入职登记花名册 | 前台按"部门+事项"翻册子 | 员工按 SOP 流程干活 |

> 🔗 对照学过的：Ioc · 拦截器 · 设计模式 · spring

### 看新代码的口诀

先别急着读方法体：
1. 先找"**登记表**"（通常是 Map / List / 启动扫描的注解）
2. 再找"**查表的人**"（getXxx 方法）
3. 最后看"**查出来的东西怎么被调用**"

这三处找到，框架骨架就清楚了，剩下全是业务细节。

## 四、举一反三三招

1. **三段论**：注册 / 路由 / 执行，看什么都先套这三问
2. **找变与不变**：拿到需求先问"哪些步骤所有情况都一样，哪些会因情况而异"→ 一样做骨架，异的定义成接口让别人填
3. **长流程配后悔药**：一件事分好几步且中途可能失败 → 每步配一个"撤销"动作，失败时倒着执行。下单、转账、发优惠券全是这个套路

### 什么时候往自己项目里套

- **信号一**："同一个动作，不同类型的东西做法不同"（不同支付渠道、不同推送方式）→ 用 **接口 + 注册表路由** 消灭 if-else
- **信号二**："一件事分多步，中途失败要能撤销" → 用 **责任链 + 逆序补偿**

## 五、和规则引擎（Drools）的区别 ⚠️ 面试易混淆

memberclub 双引擎**不是规则引擎**（之前容易看走眼）：

| | 规则引擎（Drools） | memberclub 双引擎 |
| :--- | :--- | :--- |
| 核心机制 | 事实 + 规则集 + Rete 匹配算法 | HashMap/Table 查表 + for 循环责任链 |
| 规则放哪 | 数据/配置，可热更新 | 硬编码在 Java 类里 |
| 本质 | "哪些条件成立就执行" | "按标签查路由 + 按顺序执行" |
| 模式归属 | 推理引擎 | **策略模式 + 注册表 + 责任链**（简化版 SPI） |

它也**不是 AOP**：AOP 是"代理对象包住方法调用"（透明拦截），双引擎是"调用者自己先查表挑人再调"（显式路由）。项目里真正的 AOP 只有日志、重试那几个切面。

> 🔗 对照：规则引擎（drools） · 规则引擎，业务架构亮点 · aop

## 六、上手路径（只学引擎，1~2 天）

1. 打开 `memberclub.common/.../extension/ExtensionManager.java`（已加注释），只看两个方法：`init()`（登记进表）、`getExtension()`（翻表找人）
2. 打开 `memberclub.common/.../flow/FlowChainService.java`，30 行主算法，对照"后悔药"逻辑
3. 跑 `TestFlow` / `ExtensionTest` 单测打断点验证
4. 练手：给 demomember 加一个新 scene，体验"只写差异部分"

### 必记的三个源码级细节

- **失败节点自己不留后事**：index 只在 process 成功后 +1，C 失败时补偿从 B 逆序走，**C 自己收不到 rollback**（半途脏状态靠 process 内部 try/catch 自清理）
- **SkipException 不是异常**：不回滚、不抛出，抛它的节点自己一个钩子都收不到
- **注册 key = 接口名_bizType_scene**，key 冲突直接抛异常（fail-fast 防线上路由错乱）
