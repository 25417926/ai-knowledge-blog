# 大模型的两个硬约束

大模型的多数工程手段，都是在跟两个约束打交道：它会编，它记不住太长的东西。前者催生了检索与引用，后者催生了压缩与拆解。

## 一、大模型的两大核心局限

### 1. 幻觉问题（Hallucination）

> [!def] 定义
> 模型生成看似合理，但事实错误、虚构或无中生有的信息。

- **典型案例**：虚构学术论文——标题、作者、发表日期与真实情况不符。
- **三大成因**
  1. **概率预测本质**：模型本质是"文字接龙"，按概率预测下一个 token，而非基于事实推理。
  2. **训练数据缺陷**：数据中存在错误、偏见或已过时信息。
  3. **缺乏内置事实核查**：模型自身没有验证机制。
- **应对四法**
  1. 交叉验证（多源比对）
  2. 要求模型提供来源 / 引用
  3. 采用 RAG 技术（见下文）
  4. 人工确认（高安全领域必备）

### 2. 上下文窗口限制

> [!def] 定义
> 模型单次能处理的最大「输入 + 输出」长度，以 token 为单位。

- **演进**：GPT-3.5 初期约 5K token → 当前已达 200K token。
- **主要影响**：长文档处理、多轮对话、复杂任务受限。
- **缓解手段**
  - 滑动窗口
  - 摘要压缩
  - RAG 外存检索
  - 任务分段拆解

## 二、大模型应用开发四大方向

### 1. 提示词工程（Prompt Engineering）

- **本质**：人机交互的唯一接口。
- **四项原则**：角色定位 + 任务说明 + 具体要求 + 输出格式。
- **类比**：像管理一个"腼腆但博学的员工"——必须给出清晰指令，才能驱动其产出。

### 2. 检索增强生成（RAG）

- **本质**："开卷考试"——将私有知识注入向量数据库，推理时实时检索并补充上下文。
- **核心价值**
  - 缓解幻觉
  - 适配垂直领域（法律 / 医疗 / 金融）
  - 适合做客服助手
  - 实施成本低

### 3. 智能体（Agent）

- **四大能力**：自主理解 → 规划 → 执行 → 反思。
- **适用场景**：简单 RAG 或固定逻辑控制无法满足的复杂企业级应用。

### 4. 模型微调（Fine-tuning）

- **适用条件**：提示词、RAG、Agent 都失效时的最后手段。
- **两大障碍**
  - 数据质量（清洗 / 标注）
  - 算力成本（尤其是高质量标注）
- **主流路径**：先用 RAG / Agent 收集用户反馈数据，再迭代微调。

> [!info] 四种方案的选型顺序
> 提示词工程 → RAG → Agent → 微调。越往后成本与门槛越高，应优先尝试轻量方案。

## 三、职业发展与学习建议

### 行业应用前景

教育（国家政策支持）、医疗（辅助分诊 / 审核）、金融（量化分析）、法律（合同审查 / 案例检索）、制造 / 营销 / 财务（票据审核 / 流程自动化）。

### 核心就业岗位

| 岗位 | 侧重点 |
| --- | --- |
| AI 产品经理 | 需求洞察与跨团队协作 |
| AI 应用开发工程师 | 编码与工程落地 |
| AI 训练师 | 数据清洗与算法微调（学历与数学要求高） |

### 上手路径

- 先跑通一次最小闭环：拿官方 SDK 调一次对话接口，确认 key、模型名、返回结构都对。
- 再写 5 条真实的提示词（不追求优化，先记录真实需求），作为后面调优的基线。

> [!quote] 核心理念
> 不是 AI 取代人类，而是**会用 AI 的人取代不会用 AI 的人**。
