# 提示工程的结构化写法

把提示词当成**一个函数的签名**来设计，会比"调语气"有效得多。

## 五段式结构

1. **角色**：模型是谁。一句话足够，写太多反而稀释注意力。
2. **上下文**：它能依据什么。RAG 检索到的片段放这一层。
3. **任务**：要它做什么。用动词开头，一次只给一个任务。
4. **约束**：不许做什么。"只依据给定资料回答"这类否定约束必须显式写。
5. **输出格式**：结构化输出优先给 JSON Schema 或明确的分节标题，不要靠"请用列表"这种模糊描述。

## 三个实际经验

**经验一：约束放在任务之后。** 先说要做什么再说不许做什么，模型对近处的指令更敏感。

**经验二：少样本示例比形容词有效。** "简洁一些"没用，给两个正例一个反例立刻见效。

**经验三：输出格式要能被程序校验。** 如果下游要解析，就必须要求结构化输出并在代码里做校验与重试，而不是假设模型一定听话。

## 与系统设计的关系

提示词是 Agent 里最容易被当作"魔法"的一层。把它当接口设计的好处是：**可版本化、可回归测试、可替换**。当回答质量下降时，你能判断是提示词退化还是检索退化。
